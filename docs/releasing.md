# Подготовка выпуска

Новый `submit → handle` API требует major-перехода. Версия4.0.0 опубликована; для следующего кандидата проверяйте точную identity заново и не подменяйте её старым npm latest. Version/changelog, tag, push и публикация — отдельные действия, каждое выполняется в согласованном объёме.

## Проверить содержание кандидата

1. Согласовать номер major-версии. Описать breaking changes понятными потребителю пунктами и дать ссылку на [миграцию](migration.md); автосписок commit titles этого не заменяет.
2. Сверить README, [API](api.md), [AGENTS.md](../AGENTS.md) и [разработку](development.md) с source и actual scripts. Публичные документы не должны зависеть от локальных планов/передач. Проверить все локальные ссылки и доступность ссылок README из npm.
3. Зафиксировать ровно предназначенный release commit. После изменения manifest/README/build inputs заново получить нужные package checks; не выдавать старый tarball за новый кандидат.
4. Получить successful Actions для этого commit. Проверить head_sha, conclusion всех jobs и происхождение runtime-package artifact; сверить SHA256SUMS и состав архива. Полный package job и runtime smoke artifact — разные подтверждения, оба должны относиться к кандидату.
5. Убедиться, что tarball содержит только ожидаемые package.json/README/LICENSE/src/build/src и не содержит local state, secrets, tests или samples. Production source payload и manifest оценивать отдельно: pnpm normalizes packageManager/scripts.prepack, compressed SHA разных pack tools может отличаться.

Изменение Markdown само по себе не требует повторять runtime tests локально. README входит в пакет: после последней содержательной правки перед выпуском нужен новый artifact для финального кандидата. Это не отменяет прежние доказательства неизменённого кода, но связывает поставку с её актуальным содержимым.

## Разделить подготовку и публикацию

`pnpm release` запускает np и не является безопасным сокращением для подготовки одного changelog. Package script `version` запускает auto-changelog и git add CHANGELOG.md. Перед любой такой командой прочитайте её actual поведение и убедитесь, что весь её scope разрешён.

До отдельного разрешения на выпуск не создавайте tag/release, не публикуйте npm и не меняйте dist-tags. Подготовка локальных изменений и проверка артефакта не означают, что публикация разрешена. Успешный CI также не доказывает проверку на настоящем аккаунте, оптимальный pacing, exactly-once или account-wide защиту.

## После разрешённой публикации

Проверить опубликованную версию, содержимое tarball, imports/types и соответствие README/tag документации. Обновить сообщение о статусе поставки только после фактической публикации. Оставить миграцию и указание breaking changes доступными для потребителей старого API.
