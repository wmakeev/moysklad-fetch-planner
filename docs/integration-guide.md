# Интеграция и эксплуатационная проверка

Руководство для агента, подключающего библиотеку к системе массового обмена с МойСклад. Короткий маршрут — [руководство агента](agent-guide.md), условия API — [справочник](api.md). Здесь выбирают необходимые прикладные проверки, наблюдение и действия при отказах; сам collector/exporter или эксплуатационный эксперимент библиотека не предоставляет.

## 1. Установить исходный контракт

1. Зафиксировать точную поставку, Node, transport family и конфигурацию. По [маршруту получения артефакта](agent-guide.md) связать установленный tarball с нужным commit и успешными проверками.
2. Сверить использование с [API](api.md), [public exports](../src/index.ts) и декларациями установленного пакета. Submit возвращает handle; result и resourcesDone имеют разный смысл. Прозрачной Fetch-подстановки в SDK нет.
3. Для изменения самой библиотеки читать [AGENTS.md](../AGENTS.md), [архитектуру](architecture.md) и [разработку](development.md). При расхождении документации, типов и фактического поведения фиксировать конкретное расхождение до изменения гарантии.
4. Локальные проверки и Actions не подтверждают account-wide безопасность, произвольный producer или оптимальную скорость на настоящем API. Проверки ниже выбираются по профилю потребителя и не требуют автоматически запускать live-нагрузку.

## 2. Описать потребителя до настройки чисел

В интегрирующем проекте сохранить короткую карточку. Не переносить сюда production credentials, реальные URL с параметрами или данные клиентов.

| Поле карточки | Что записать |
| --- | --- |
| Полезная единица работы | Например, обработанная страница или документ; правило бизнес-успеха и частичного результата |
| Классы операций | Ограниченный перечень чтений/записей/загрузок, примерные размеры body и длительности; без entity IDs |
| Поступление работы | Обычный темп, всплески, длительность массовой задачи, допустимое ожидание и возможность замедлить producer |
| Область лимитов | Какие instances/процессы и другие интеграции обращаются с тем же серверным бюджетом; где карта неполна |
| Владение ресурсами | Кто создаёт и прекращает producer, читает body, очищает временный результат, публикует business value |
| Безопасность повторов | Основание serverSafe и consumeSafe по каждому классу; действия при неизвестном исходе записи |
| Цели | Допустимые latency/ошибки, необходимая полезная производительность и время восстановления; если ещё неизвестны — явно не заданы |
| Эксплуатационная ответственность | Кто разбирает guard stop, зависший cleanup, неизвестный исход записи и отказ телеметрии; кто разрешает возобновление |

Не выбирать число planner по числу workers автоматически. Один экземпляр координирует только свой поток; несколько экземпляров не получают общего guard или разрешения расходовать один и тот же бюджет независимо. До запуска массового обмена определить область координации внешней системы. Отдельный distributed limiter этим руководством не предписывается.

## 3. Встроить владение операцией

1. Оставить у planner единственную ответственность за scheduling его HTTP-попыток. Внешний producer выдаёт ограниченные окна работы и принимает backpressure. Не строить поверх него второй retry-loop, который заново submit-ит отказ без учёта причины, replay safety и общего бюджета бизнесзадачи.
2. В spec задавать method и обе replay flags явно. Значение true подкреплять свойством бизнесоперации и прикладной обработки, а не одним GET/POST или фактом получения429. Для PUT определить единое соглашение entityKey в пределах экземпляра; не включать секреты или сырой URL.
3. Каждый prepare создаёт fresh init/body с тем же логическим содержимым. Method/signal принадлежат coordinator, готовый Request не подставляется. Выбрать одну transport family; отключить или явно исключить скрытые transport retries. Redirects и входы в fetch не считать точным числом wire sends.
4. Ресурс регистрировать через onDispose сразу после acquisition до следующего await. Код приобретения сам отвечает за частичный acquisition до регистрации. Для upload нужен работающий stop-and-wait disposer: остановить источник, затем дождаться известных чтений/pull/handles. Один abort или ранний Response этого не доказывает.
5. Consume полностью await-ит чтение и свою работу, возвращает законченный T. Не отдавать наружу живой Response/reader/stream и не прятать detached работу за успешным возвратом. Non429 HTTP-ответы, бизнесошибки и mixed bulk разбирает приложение. Помечать retryableReadFailure только для известной ошибки чтения в её действующем consume lifetime, а не для любой ошибки parser/БД.
6. Временные результаты регистрировать через onDiscard. Публикацию, rename, сообщение или прикладной commit выполнять после принятого result. Отмена до resultCommitted должна привести к discard, после него успех уже сохраняется даже при cleanup pending/failed.
7. Учитывать каждый возвращённый handle, включая id=0: нематериализованный отказ submit приходит через result, не создаёт индивидуальных events и не занимает sequence. Сразу присоединять обработку обеих ветвей result и отслеживать resourcesDone. Не создавать необработанную производную Promise-цепочку своим logger/exporter. id=0 не использовать как уникальный ключ операции.
8. При внешнем AbortSignal самостоятельно связать его с handle.abort: учесть уже отменённый signal, установить listener и проверить отсутствие пропущенной отмены до продолжения работы. Снять внешний listener после окончания нужного периода наблюдения. Не передавать этот signal через init, не выдумывать signal option в submit. Запоздалую отмену и result race обрабатывать по сохранённому исходу handle.
9. Hooks подключать только для конкретного veto/defer сценария. Из prepare/consume/dispose/hooks не submit-ить зависимую работу того же planner. Observation оставлять read-only; return listener не является permit или управляющим решением.

Для resourcesDone сохранять только необходимые ссылки и безопасную корреляцию. После результата не хранить Completed.value внутри долгоживущей telemetry registry. Если cleanup завис, его pending должен быть виден даже после отказа result; удаление диагностической записи не освобождает библиотечные ресурсы.

## 4. Выбрать минимальную телеметрию

Начать с агрегатов и ограниченной скалярной корреляции, без новой зависимости или framework внутри библиотеки. Названия ниже — предлагаемые метрики приложения, а не существующие exports библиотеки.

| Набор | Как получить | Для чего использовать |
| --- | --- | --- |
| Submitted / accepted / rejected по code | Обёртка submit: id>0 означает принятую операцию, id=0 — отказ в принятии; code отказа из result. Ошибки уже принятой операции и constructor/observe throws учитывать отдельно | Замечать перегрузку и ошибки интеграции, включая sentinel handles без events |
| Dispatch / repeat dispatch / observed receipts по status | Одна planner.observe подписка до первого submit; dispatch-started, dispatchCalls>1, headers-received | Считать полезный и повторный трафик раздельно, не только финальный status |
| Result outcome / HTTP / business outcome | result/error и собственный parser | Различать успешный Promise, HTTP2xx и полезно выполненную работу |
| Очередь и занятость | Периодический planner.snapshot: queued, leasedAttempts, sentActive, effectiveParallelism, stopped, guardOpen | Отличать ожидание ёмкости, возможную коррекцию и окончательную остановку |
| Latency и возраст незавершённого | Монотонные часы submit/result/resourcesDone, пары событий одного attempt, возраст pending | Видеть очередь, хвосты ожидания и cleanup после результата |
| Resources | Completed.cleanup, ResourceSummary.resources и количество ожидающих resourcesDone | Выявлять pending/failed/unknown, не записывая их как released |
| Состояние host и collector | Штатные память/event-loop метрики; собственные ошибки/потери/возраст экспортируемых данных | Проверять накладные расходы и достоверность наблюдения |

Минимальная полезная панель показывает на общей временной шкале поступление работы, business goodput, dispatch rate, долю повторных dispatch, частоту429, очередь, leases/sent, resources pending и guard/stop. Это перечень представлений для будущего приложения, не уже созданная панель. Периоды и SLO выбираются после описания нагрузки; не подставлять универсальные численные пороги.

### Правила collector

- Установить planner observer до потока. Observe возвращает атомарный snapshot вместе с unsubscribe; initial snapshot не приходит в callback, история не повторяется. Created может быть доставлен ещё до возврата submit: общие счётчики не должны зависеть от уже готовой таблицы id→категория. Если нужна категоризация, связать её с handle после возврата и явно обрабатывать короткий период неполной корреляции без неограниченного буфера. Для основного набора достаточно агрегатов без endpoint categories.
- Event.sequence — порядок событий данного planner, не operation count. Не считать событие повторно через handle и planner. Snapshot gauges не суммировать между samples; retry-scheduled не считать состоявшимся dispatch. Attempts включает prepare без отправки.
- Поздний headers-received считать отдельно от логического result. OperationError уже выдан и не дополняется поздними status/serverOutcome; terminal snapshot может узнать новый status. Не снимать наблюдение сразу после result rejection. Не объявлять observed receipts полным счётчиком серверных запросов или внутренней истории guard: часть информации может отсутствовать из-за ошибок материализации, позднего подключения или потерь collector.
- Сначала измерять submit→result и result→resourcesDone, затем при необходимости own prepare/consume/dispose/hooks. Интервалы phase — время состояния coordinator, не точная длительность callback: preparing включает beforeDispatch, а terminal может сохраняться при ещё работающем callback. Callback wrapper должен сохранять receiver, аргументы, значение/ошибку и обработку Promise; его эквивалентность проверяется локально. Не превращать user callback timeout в утверждение о завершении его работы. Внешний wrapper не измеряет точно внутреннюю ассимиляцию и getter lifetime.
- Для durations использовать одни монотонные часы. Event.epochTime — настенные часы для отображения, они могут сдвигаться; event.elapsedMs относится к старту planner. ServerNotBefore — абсолютная отметка внутренней монотонной шкалы, а не длительность паузы. Не вычитать из неё Date.now или event.elapsedMs. Для сравнения процессов нужна отдельная временная привязка с известной погрешностью.
- Не рассчитывать точное время server pause из общего ready wait: туда входят разные причины ожидания. Не добавлять control hooks только ради timestamp. Числовые guard counters, diagnostics и полный retry decision reason сейчас не public metrics. Подробнее — [границы наблюдаемости](high-load-rationale.md#что-сейчас-не-видно-через-observation).
- Использовать bounded labels: fixed code/status и небольшой согласованный набор классов. Operation ID оставлять для краткоживущей корреляции внутри instance, не label временного ряда. Не экспортировать URL/query, entityKey, credentials, headers целиком, payload/value или Error/cause; хеширование не устраняет высокую cardinality и не гарантирует приватность.
- Listener выполняет короткую синхронную агрегацию. Export работает через ограниченный буфер с собственными обработанными rejection, счётчиком потерь и признаком работоспособности. Ошибки observer изолируются planner, но внутренний OBSERVER_FAILED не является доступным приложению оповещением. Успешный result не доказывает, что telemetry export работает.
- После resourcesDone удалять временную корреляцию. Pending означает незавершённую известную работу, а не доказанную утечку; различать ожидаемую длительную работу, отсутствие прогресса owner и рост удерживаемой памяти. Зависшие работы учитывать возрастом; retention подробностей ограничивать без подмены pending на released. Failed/unknown после resourcesDone означает завершённый учёт известных работ без доказанного освобождения всех ресурсов. Отдельно измерять память collector, registry и exporter. Лимит числа операций не ограничивает размер body/замыканий или число registrations.

## 5. Выбрать локальные сценарии интеграции

Это кандидаты тестов внешнего приложения, а не новый обязательный gate рефакторинга. Сначала проверить, какие сценарии уже покрыты библиотекой и где нужно доказать именно интеграционные callbacks/адаптеры. Все fault injections ниже предназначены controlled fake/локальному серверу; не провоцировать отказы и блокировки настоящего API.

| Сценарий | Ожидаемое поведение потребителя | Что сохранить как evidence |
| --- | --- | --- |
| Обычное чтение до конца | Содержимое проверено, result и resourcesDone обработаны | Отдельные business outcome, status и resources; нет живого body наружу |
| Non429 business error / mixed bulk / HTML | Приложение сохраняет подробности и частичные результаты, не запускает слепой повтор всей записи | Завершённый прикладной результат или cause в тесте, отсутствие дублей и утечки деталей в telemetry |
| Safe429 с последующей успешной попыткой | Fresh prepare, одна логическая identity, общий scheduler, уборка до повтора | Dispatch/attempt trace, неизменный payload, один окончательный результат; retry-scheduled отделён от dispatch |
| Transport failure и unsafe write | False replay flags не дают автоматического повтора; неизвестный server outcome отправляется на прикладную сверку | Число входов F и отдельный результат reconciliation локального сервера |
| Body read failure2xx против parser failure | Только явно разрешённый branded read failure становится кандидатом повтора; parser/БД ошибки не маскируются | Code/status/cause в тесте, число dispatch, корректный discard |
| Переполнение producer / очереди | Backpressure ограничивает выдачу работы, QUEUE_FULL учитывается даже без events | Все submit outcomes и отсутствие повторного бесконечного resubmit-loop |
| Отмена до отправки / в полёте | До dispatch ничего не отправлено; после dispatch исход сервера не угадывается | Result/error, поздний status отдельно, resourcesDone и освобождение внешнего abort listener |
| Отмена до/после resultCommitted | До commit временный результат discarded, после commit value сохраняется | Доставка либо discard, без потери и двойной публикации |
| Early429 при незавершённом upload | Собственный disposer останавливает и ждёт producer; новый upload не стартует до cleanup | Barrier источника, attempts/dispatch и leases/sent до/после release |
| Pending и failing cleanup | Приложение не теряет value после commit, не считает failed/unknown released и замечает возраст pending | Result latency, pending age, конечный ResourceSummary; fake deferred освобождается в finally |
| Hook deny/defer/timeout, если hooks используются | Callback не создаёт nested submit, поздний allow не возобновляет terminal работу | Собственная policy причина без secrets, итоговый code и отсутствие запрещённой отправки |
| Guard stop и последующие поздние receipts | Producer прекращается; instance не пересоздаётся автоматически для обхода защиты | Момент guardOpen/stopped, уже отправленная работа и поздние статусы отдельно |
| Shutdown и отказ exporter | Нет потерянных result rejection, pending работы учтены, остановка наблюдения не меняет policy | Полнота реестра handles, unresolved cleanup и собственные потери telemetry |

Fake deferred, серверы, readers и producers освобождать в finally; watchdog означает отказ теста, а не физическое завершение работы. Параметры текущих library tests служат примером проверки инвариантов, не готовыми production SLO. [Раздел проверок обоснования](high-load-rationale.md#проверки-и-данные-для-архитектурных-выводов) описывает более широкие гипотезы и пределы выводов.

## 6. Начать эксплуатационную оценку с пассивного наблюдения

1. После разрешённого подключения собирать обычный поток, не увеличивая нагрузку ради измерения. Отметить интервалы полноты telemetry, конфигурацию и конкурирующую нагрузку, насколько она известна. Не начинать с поиска максимального числа requests/sec.
2. Посчитать business goodput, dispatch rate, retry share, ошибки и latency по одним временным интервалам. Для операций показывать также отклонённые, незавершённые и возраст pending; p99 только завершённых success не отражает starvation.
3. Сопоставить рост очереди с наличием backlog, изменением server signals, leases/sent и временем callbacks. Отсутствие429 при низкой полезной работе не доказывает хороший pacing, высокая частота dispatch может оказаться преимущественно повторами.
4. Распределения durations сначала разделить по ограниченным классам, особенно короткое чтение и тяжёлый bulk/upload. При необходимости измерить body read отдельно от decode/БД. Не повышать attempt/deadline по одному timeout: после отправки он не доказывает отмены записи.
5. Определить SLO и оповещения по бизнеснеобходимости и полученному baseline: допустимое ожидание, возраст pending, длительность восстановления и потери exporter. Для каждого сигнала указать ответственного и действие; точные пороги не выводятся из defaults библиотеки.

Если данных недостаточно или collector терял события, вывод ограничить этим фактом. Пассивная telemetry не доказывает предельную пропускную способность и не проверяет аварийный сценарий, которого не было.

## 7. Разбирать отклонения в установленном порядке

| Наблюдение | Что проверить сначала | Действие до архитектурного изменения |
| --- | --- | --- |
| Очередь растёт, QUEUE_FULL | Входящий темп, server pause, занятость leases, длительность own callbacks | Замедлить producer штатным способом; не увеличивать очередь как средство ускорения |
| Частые429 | Единая ли область coordination, нет ли соседней нагрузки/скрытых retries, как меняются goodput и effective limit | Сохранить общий backoff; не добавлять обходной retry и не повышать concurrency по одному backlog |
| Guard открыт | Причины HTTP/API ошибок, повторный трафик, область одного instance, поздние receipts | Прекратить producer, устранить причину; возобновление принимает назначенный ответственный |
| PUT_LIMIT / GUARD_CAPACITY | Соглашение entityKey, повторяющиеся обновления, число живых keys | Исправить группировку/поток, если он неверен; не менять key ради обхода лимита и не считать отказ общим stop |
| Result окончен, resources долго pending | Prepare/consume/hook/disposer, stop-and-wait barrier и age | Исправить owner или источник; не освобождать lease внешним timeout фиктивно |
| Низкий goodput без явных429 | Есть ли входящая работа, где заняты leases/sent, body vs БД/CPU, задержка host/collector | Проверить границу consume и стоимость наблюдения на локальном сравнении |
| Много deadline/attempt timeout | Очередь, длительности по классам, retry waits и собственные callbacks | Сначала определить причину и нужный бизнесбюджет; не делать timeout автоматическим признаком безопасного resubmit |
| Failed/unknown resources | Ошибки disposer/read/cancel, удержанный reader lock и сторонний producer | Разобрать конкретное освобождение; повтор HTTP не лечит cleanup |
| Telemetry внезапно тиха | Collector/exporter health, потери, subscriptions и полнота окна | Восстановить наблюдаемость; отсутствие событий не объявлять отсутствием ошибок |

Guard ограничивает новые dispatch после своего решения, но не отзывает уже отправленное и не ограничивает жёстко число будущих receipts. При разборе stop учитывать запросы в полёте и другие instances. Состояние serverOutcome=unknown требует прикладного reconciliation по устойчивой identity; если надёжной проверки нет, не считать повтор записи безопасным.

## 8. Завершать работу и возобновлять её осознанно

Для планового shutdown сначала прекратить producer. Если нужно закончить уже принятую очередь, оставить planner работающим и ждать result/resourcesDone всех возвращённых handles в пределах собственного окна shutdown; затем вызвать stop. Если нужно сразу запретить новые отправки, вызвать stop сразу: queued/retry-wait/preparing/ready операции будут отклонены, а не доведены до отправки. Stop возвращает void, запрещает новые отправки/повторы и не abort-ит уже sent попытку; он не заменяет drain. В обоих вариантах продолжать учёт handles. Внешнее приложение определяет, нужно ли дополнительно отменить конкретные handles, учитывая unknown server outcome.

Задать собственное окно shutdown. Если оно закончилось, перечислить безопасные сведения о unresolved работе и применить согласованную политику host; ожидание с timeout не превращает ресурсы в released. Завершение процесса также не отменяет уже возможный commit на сервере. Observation снимать после нужного периода учёта, а exporter завершать отдельно, сохраняя сведения о потерях.

После guard stop нет автоматического восстановления того же instance. Перед созданием нового убедиться, что причина серии ошибок устранена, завершённые/неопределённые записи сверены, известна оставшаяся работа и учтено внешнее серверное окно. Задержка сама по себе не доказывает безопасность нового запуска; новая локальная история guard не должна маскировать предыдущую серию.

## 9. При необходимости сравнить варианты

Если пассивные данные показывают возможный недостаток pacing или границы consume, сформулировать одну проверяемую гипотезу. Сначала использовать локальный эмулятор с известным бюджетом, задержками и сериями ответов. Сравнивать текущую адаптацию с простой фиксированной rate/concurrency политикой при одинаковых replay safety, cleanup, guard, бюджете попыток/времени и внешнем потоке поступления.

Включать steady backlog, burst, временную деградацию и восстановление. Использовать воспроизводимые seeds, повторения и разброс результатов. Сохранять rejected/pending хвост за границей окна; сравнивать goodput, latency,429, долю retries, память и recovery вместе. Разница в количестве завершённой полезной работы — результат, а не повод исключить неудобные операции из сравнения.

Эксперимент на реальном API с повышением нагрузки, намеренными ошибками или риском записи требует отдельного разрешения и границ. Локальная модель доказывает только свойства своей модели; не переносить её максимум throughput на МойСклад. Здесь такие эксперименты не поручены.

## 10. Зафиксировать вывод по данным

В потребляющем проекте записать профиль и конфигурацию, период наблюдения и его полноту, выбранные сценарии и результаты, goodput/ошибки/latency/pending, выявленные причины и принятое действие. Для каждого архитектурного вопроса из [обоснования](high-load-rationale.md#сомнения-и-условия-пересмотра) выбрать: подтверждён в указанной области, есть контрпример или данных недостаточно. Не подменять последний вариант общим «всё работает».

Основания для изменений различаются: ошибка owner требует исправления интеграции; неподходящий бюджет — обоснованной настройки; повторяемая ошибка использования — улучшения документации или адаптера; воспроизводимое ограничение границы — отдельного архитектурного решения. Редко используемую возможность нельзя удалять только из-за отсутствия incidents; сначала проверить, какую принятую гарантию она обеспечивает.

Руководство можно применять выборочно: для первого потребителя достаточно карточки, минимальной telemetry и сценариев реально используемых операций. Остальные проверки добавляются при соответствующих рисках. Это ограничивает стоимость интеграции без ослабления заявленных библиотекой гарантий [PARETO, VERIFY].
