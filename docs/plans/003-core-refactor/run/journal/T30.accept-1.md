## Краевые пути и контракт

- resolve/reject проверены счётчиками реальных callbacks action через инструментирование settleAction только в независимом JS-пробнике; release — счётчиком protected hook и фактическими inflight getters. На success ровно resolve1/reject0/release1; на sync throw, transport reject, response observer/header failure — resolve0/reject1/release1. После нескольких шагов clocks повторных стартов и завершений нет.
- Из request/response/fetch-error callback поставлены сразу два новых action и затем брошено исключение; порядок трёх starts сохранён, callbacks resolve2/reject1, release3, очередь и inflight пусты. Для каждого callback повторено с работающим и бросающим diagnostic path. Исходный Error сохраняет identity, fetch-error вызывается один раз.
- После throw request observer action немедленно отвергнут, но отправленный transport удерживает inflight1 и не допускает следующий action даже после продвижения времени на300мс. Проверены поздний success, поздний429 с invalid header и поздний reject: поздние результаты не эмитят response/fetch-error повторно, не возвращаются в retry и освобождают слот один раз; затем очередь продолжает работу. Непереданный ответ уходит в cleanup ровно один раз, rejected cancel наблюдается без unhandled.
- Non429 header/response observer failure: Response сохраняется у planner до вызова cleanup; потребителю достаётся ошибка. Успешно доставленный Response тот же объект, cancel не вызван, тело читается без изменения. Полная матрица T60 не заявляется закрытой.
- Фиксированная диагностика проверена точным набором аргументов ['FetchPlanner observer failed']; URL и сообщения исходной/вторичной ошибки не передаются. Штатный child error-observer проверяет реальный stderr и отсутствие private message/URL. Отдельно проверен throw самого process.emitWarning.
- Три штатных strict child завершаются exit0 естественно, watchdog не сработал. Независимый strict child последовательно проверил sync throw, rejected transport, request/response observer failures с вторичным fetch-error throw и бросающей диагностикой; после каждого продолжилась очередь и inflight стал0. Нет process.exit, unref или обращения к private timers для завершения.
- У внутренних promise chain есть terminal catch, поздний transport rejection наблюдается, cancel rejection имеет catch. Независимые strict-пробы не дали uncaught/unhandled. Async listeners, чужие throwing subclass hooks и новые retry-политики контрактом T30 не обещаны.
- Все прежние 36 сценариев остаются зелёными, включая прежние GET/POST/Response/event/EventEmitter/FIFO и slot сценарии.
