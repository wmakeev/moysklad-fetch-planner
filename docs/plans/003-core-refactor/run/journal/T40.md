## Решение и разрешённое сопряжение [ROOT, ALT, VERIFY, CONSIST, SURFACE]

Выбран один общий serverNotBefore в monotonic миллисекундах; каждое корректное rate429 обновляет его максимумом прежнего и receipt + retryAfter. Enqueue, transport completion/finally и callback enqueue сходятся в pump; он владеет единственным scheduling timeout, при пустой очереди или занятой capacity timeout снимается. Альтернатива отдельных задержек каждого finally/callback отклонена: именно независимое перепланирование позволяло перезаписать общий запрет старта (red D05 ниже). scheduleWake сохраняет полный deadline, ставит только bounded chunk <=2147483647 и проверяет владение callback до любого действия. Прежний timeout заменяется и при продлении паузы.

Внутренние elapsed/correction timestamps переведены на единый monotonic clock без изменения формулы, таблицы101, jitter, defaults и correction clamp/recovery policy. Публичные request/response/error timestamps остаются wall clock; getNextRequestTime переводит остаток внутреннего deadline в текущий Unix timestamp либо возвращает0 без wake. getOptions mutable, errorLimits и legacy429005 сохранены. Публичного adapter/injection/timer instrumentation не добавлено; runtime.ts — внутренние часы и верхняя граница timer chunk. T30 terminal settlement, observer containment, поздний transport и ownership cleanup path сохранены.

Минимальная адаптация test/index.test.ts отдельно разрешена оркестратором в текущем диалоге после обнаружения конфликта прежних fake timers с monotonic временем. Три названных теста: FetchPlanner (parallel limit and throttling), FetchPlanner (retry 429 TooManyRequests error), FetchPlanner (retry 429 parallel limit overflow error). Они раньше продвигали только setTimeout, оставляя часы интервалов неподвижными; теперь используют тот же createRuntime, синхронный tick сохраняет порядок assertions. В третьем тесте ожидания700/300мс заменены управляемыми advance с теми же числами, а новые запросы стартуют через tick0. Все исходные сценарии/assertions и допуски сохранены. package.json меняет только явный test:unit entrypoint, добавляя scheduler suite.

Harness управляет performance.now независимо от Date.now; wall jumps меняют только offset Date.now, не шкалу fake timers. Первоначальная попытка jumpWall через MockTimers.setTime оказалась связана с очередью timers: forward jump вызывал повторные wake внутри tick. Неудачный пробный запуск остановлен SIGTERM только своего scheduler child; эта версия harness исправлена до check/coverage. Успешные конечные сценарии не используют process.exit/unref/доступ к private timer cleanup. Наблюдение таймеров сделано test-scoped mocks глобальных setTimeout/clearTimeout; восстановление globals проходит существующий T10 test.

## Матрица исполняемых утверждений

- D05 shared pause/success и enqueue: два inflight; receipt429 с400мс; starts остаётся2 на399мс, retry разрешён на400мс. Red получен до production правок, по assertion No start before receipt + 400ms, а не по диагностическому exit.
- Wall clock +10000000 и -900000мс: performance.now не меняется, getNextRequestTime == Date.now()+400, затем +1 на399мс; starts только на400, после drain getter0.
- Deadlines2147483647/2147483648: starts запрещены до конца первого bounded chunk; для2147483648 после2147483647 остаётся1мс и один timeout, старт только после остатка. Все переданные delays в[0,2147483647], TimeoutOverflowWarning отсутствует.
- Два429 с receipt на0 и100мс, второй hint100 или500: deadline соответственно400 или600; поздний короткий hint не сокращает паузу, длинный заменяет wake. Вручную вызван отменённый callback: ни старта, ни второго timeout; после drain он также не запускает action. FIFO retry сохраняет прежний unshift order: b,a.
- Response callback enqueue при429 и success headers второго inflight на100мс: свежий remaining10/10 и finally не сокращают400мс; повторные enqueue/pump не создают второй timeout.
- Pacing при remaining0, interval1000, maxDelay1000, coefficient1: server boundary400 недостаточен; starts запрещены до999, разрешены на1000. lastRequestDelay1000.
- Terminal response observer throw после receipt429: очередь пустая, timeout отсутствует и getter0, но enqueue через100мс сохраняет оставшиеся300мс общего запрета.
- Безопасный header MAX_SAFE_INTEGER, дающий небезопасный абсолютный deadline с receipt: явный reject, только исходный timer0, повторного таймера/очереди нет.
- trackTimeouts maximum ==1 и active.size==0 после завершения проверены в нескольких сценариях; старые event/FIFO/priority/subclass hook/lifecycle и strict child остаются в полном прогоне.
