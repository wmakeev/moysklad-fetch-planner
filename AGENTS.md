# fetch-planner

## Назначение и маршрут

TypeScript/JavaScript-библиотека Node ≥24, ESM, для законченных HTTP-операций `submit → handle`. Результат операции и физическое завершение ресурсов различаются. Для интеграции библиотеки в другое приложение сначала читать [руководство агента](docs/agent-guide.md); для изменения этой библиотеки — этот файл, [разработку](docs/development.md) и relevant раздел [API](docs/api.md).

## Архитектурные границы

- Сохранять единственного coordinator admission/dispatch/retry. Observation read-only, управляющие hooks отдельны; timer wake и возврат listener не permit. Ограничения актуальны непосредственно перед transport.
- Каждая attempt получает fresh prepare/init/body. Method и signal принадлежат coordinator. Повтор требует обеих replay flags, подходящего failure, успешной известной cleanup и оставшихся budgets; method/status сами по себе не доказывают safety.
- Abort/timeout не доказывают остановку callback/upload или отсутствия серверной записи. Accounting освобождается только по фактической известной работе. До commit нужен discard, после commit готовое value сохраняется при cleanup failure/pending.
- Consume возвращает законченное значение; raw Response/reader/stream не выдаётся как готовый результат. Business identity, parsing ошибок API, публикация value и cooperative stop-and-wait producer принадлежат приложению.
- Guard/queue действуют на instance. Не обещать account-level coordination, exactly-once, остановку произвольного callback, оптимальную скорость или общий предел памяти из одного ограничения числа задач.
- Не добавлять scheduler, facade, middleware, метрики и опции без реальной потребности. Для нетривиального решения сопоставить альтернативу и указать цену; принятую гарантию нельзя молча снимать ради упрощения.
- При предположениях о МойСклад использовать доступный навык moysklad-api и актуальные первичные источники. Если навыка в окружении нет, явно отметить это и использовать первичные документы; локальные defaults не являются точной копией правил отключения vendor.

## Работа с файлами и внешними системами

- Искать через rg/rg --files/fd в этом проекте или прямо указанном пути. Исключать `.env`/`.env.*` включая example и `.explain` до stat/read/traversal/copy/hash. Не обходить root/home/соседние проекты/node_modules ради поиска, не выводить окружение или credentials.
- Не создавать worktree/checkout/копию репозитория без поручения. Не откатывать чужие правки и не редактировать чужую передачу; не запускать оркестрацию и не менять её учёт из посторонней задачи.
- `.agents`, `.vscode`, `.plans`, `.explain`, `.reports`, `__temp`, build и coverage остаются локальными; не force-add. Корневые AGENTS.md/CLAUDE.md и docs — публичные проектные инструкции; не копировать в них личные правила, секреты, machine paths или локальные review links.
- Не исполнять и не импортировать samples/stress/launchers/workers ради документации или обычной проверки, даже opt-out. Live API, аккаунты, нагрузка и внешние записи требуют отдельного явного поручения.
- Не устанавливать dependencies и не менять toolchain ради Markdown. Не запускать широкое форматирование/автоисправление. Version/changelog/push/tag/publish/release и внешние CI actions не следуют автоматически из локальной проверки; работать только в порученном scope.

## Проверки и отчёт

Проверить фактические Node/pnpm до команд. Основной setup чистого клона и TS5.7 prerequisite — [разработка](docs/development.md). При наличии локальной compatibility-среды использовать её pinned PATH; отсутствие каталога не означает, что он поставляется с проектом или его надо восстанавливать по старому receipt. Не выдавать случайный global Node за проверенную matrix.

Для source changes выполнить scoped проверки и обязательные gates порученного этапа. Не повторять полные check/coverage/package без изменённых inputs или конкретного основания. В параллельной общей копии не запускать широкий workload из отдельной документационной задачи. Для Markdown достаточно чтения результата, проверки ссылок, якорей и разметки; новые tests называются по-английски.

В отчёте различать source/type audit, fake/loopback, package acceptance, actual Actions и реальное использование. Не называть чтение кода runtime test или старый artifact свежей приёмкой. Причины незавершённого и ограничения проверки фиксировать явно; состояние Git можно снять командой, его не дублировать в передаче.

## Документация

Писать кратко по-русски. Каждый Markdown абзац, пункт списка и строка таблицы — одна строка без переноса по ширине. Команды/JSON/адреса для копирования помещать отдельными code blocks. Смысл интерфейса менять вместе с API/миграцией/related руководством; условия хранить в одном основном документе и ссылаться на него. Markdown lint infrastructure и новое средство публикации документации не вводить попутно.
